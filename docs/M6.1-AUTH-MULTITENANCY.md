# M6.1B/C — Authentication, Multi-tenancy and RBAC

## Goal

Remove tenant identity from public frontend configuration and enforce organization access on the API boundary.

## Security model

- Authentication: high-entropy opaque session token in an HttpOnly cookie.
- Session storage: only SHA-256 token hashes are persisted, allowing server-side revocation.
- Password hashing: `scrypt` with per-password random salt.
- Tenant selection: `X-PulseOps-Organization`, accepted only when the authenticated user has a membership for that organization.
- When a user belongs to exactly one organization, the tenant header may be omitted.
- Mutating browser requests require `X-PulseOps-Request: web` in addition to strict CORS and SameSite cookies.
- Cross-tenant object lookup is returned as `404` to avoid disclosing object existence.

Opaque server-side sessions were selected instead of JWT for the web product because revocation and logout are first-class requirements and no stateless token interoperability is currently needed.

## First setup

`GET /v1/auth/bootstrap-status` reports whether a first owner must be created.

In non-production environments only, `POST /v1/auth/bootstrap` creates the first user. If exactly one organization already exists, the owner membership is attached to it. If no organization exists, `organization_name` creates one.

After the first user exists, bootstrap is permanently rejected.

## Tenant invariant

Client-supplied organization identifiers are selectors, not authorization. Every tenant-scoped request verifies membership server-side before reading or mutating data.

## Deferred hardening

Before public production rollout: MFA/SSO, login rate limiting, audit log, password reset, invitation lifecycle, security headers, session cleanup/rotation policies, secret manager integration and external penetration testing.
